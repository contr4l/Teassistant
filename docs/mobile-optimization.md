# 手机端与入口优化建议

版本：V0.2（2026-11-14）。状态：第 0 节为已确认方向并进入实施，其余为建议。依据：[PRD](../PRD.md) 1.1、[设计约定](ui-guidelines.md)、`main` 分支现有代码，以及本地 390px 合成数据截图。未经真机测试；标注“需真机验证”的项目不得写成已确认事实。

## 0 已确认方向（2026-11-14）

用户要求整体 UX 贴近移动 App：所有页面都能用底部大按钮切换到工作台、考试分析、学生档案、组卷；电脑保留左侧导航；手机组卷列入本期，结果为可下载的成品 PDF；PRD 1.1 已同步更新。规则见[设计约定](ui-guidelines.md)第 8 节。

本批实施：底部标签栏与“我的”（E-09）、网址路由与返回键（E-08）、列表→详情与底部操作栏（M-03、E-04）、手机 16px 与大按钮（M-01、M-07）、两个拍照按钮与缩略图、逐文件状态、图片压缩（M-02、M-04、M-05、M-06）、工作台下一步按钮（E-01）、组卷缺少条件提示（E-07）、组卷结果下载大按钮（E-11）。其余项目保留为后续建议。执行与验收记录见 [mobile-app-ux-v1](acceptance/mobile-app-ux-v1.md)。下文中 M-10“手机只显示学生基本信息”因用户要求所有入口在手机可用而不再采用。

## 1 边界与用户

- **产品形态**（PRD 1.1，2026-11-14 更新）：手机按移动 App 方式组织，负责上传、查看状态、组卷并下载成品 PDF；逐题核对、修正、组卷预览调整以电脑为主。小程序与原生 App 不在本期范围。
- **用户画像**（用户 2026-11-14 提出）：中年初中数学教师，普遍不擅长使用电脑；可能有老花；常在课间或晚上用手机处理。
- **目标**：老师拿起手机能一次把试卷拍对、传对，并知道下一步去电脑上做什么；在电脑上每一屏都能一眼看到“现在该点哪个按钮”。

优先级：

- **P0**：只改前端，属于本期范围。
- **P1**：需要后端改动或产品取舍。
- **P2**：超出当前 PRD，需先改需求。

## 2 手机上传

| 编号 | 优先级 | 现状 | 建议 |
|---|---|---|---|
| M-01 | P0 | 输入框和下拉框为 14px；iOS Safari 在聚焦小于 16px 的输入框时会自动放大页面，老师会觉得页面乱跳、缩不回去 | 手机端表单控件统一 16px |
| M-02 | P0 | 已上传列表只显示文件名（如 `IMG_4821.jpg`），看不到图片，页序调整等于盲调 | 每页显示缩略图和醒目的“第 N 页”，可点开大图；保留并放大上下箭头（对该人群比拖拽可靠） |
| M-03 | P0 | 手机上最主要的“拍照上传”位于考试页中部，前面是考试列表和摘要卡；导航藏在左上角菜单 | 手机考试页改为一页向导：① 选学生 → ② 选考试 → ③ 拍试卷 → ④ 拍学生作答，每步一个大按钮；底部常驻标签栏替代菜单（见 E-09） |
| M-04 | P0 | 上传前要先选材料类型标签，容易把作答传进“试卷”；每拍一页都要重新操作 | “拍试卷”“拍学生作答”两个独立大按钮；拍完一页停留在当前步骤，提示“已上传第 3 页，继续拍下一页”，并提供“这一类拍完了” |
| M-05 | P0 | 上传成功只有 4.8 秒提示条，没有逐个文件的进度；弱网时老师会以为卡住而重复点击 | 每个文件常驻“上传中 / 已完成 / 失败（重试）”；失败的文件可单独重传 |
| M-06 | P0 | 手机照片通常 3–8 MB，前端不压缩，服务端上限 30 MB | 上传前在手机端压缩（建议长边约 2500px、JPEG 质量约 0.85，**需用真实卷面确认不影响识别**）；PDF 不处理 |
| M-07 | P0 | 正文 14px，对老花用户偏小 | 仅手机端：正文 16px，按钮高度 ≥48px，主按钮占满整行。这是对设计约定第 2 节 14px 规则的手机端例外，需写入约定 |
| M-08 | P0 | 传完不知道下一步 | 材料齐全后显示“材料已齐。请在电脑上打开本网站，进入这场考试开始分析”，附可复制的链接（依赖 E-08） |
| M-09 | P0 | 拍摄质量完全依赖老师 | 首次拍照前显示 3 条带示意图的提示：试卷放平、整页入框、光线均匀不反光；之后可在按钮旁随时查看 |
| M-10 | P0 | 学生档案在手机上要勾选 93 个考点，这是电脑端任务 | 手机上只显示基本信息和“已学考点请在电脑上设置” |
| M-11 | P1 | 传错的文件不能删除：后端没有删除材料的接口，前端只能排序 | 增加“删除这一页”“改为学生作答”；需新增后端接口，并确定已分析考试的材料变动如何处理 |
| M-12 | P1 | 老师很可能从微信里打开链接；微信内置浏览器的拍照、文件选择、登录保持和 PDF 下载与系统浏览器不同（**需真机验证**） | 检测到微信浏览器时提示“点右上角 … 选择‘在浏览器打开’”；确定是否把微信内置浏览器列为支持环境 |
| M-13 | P1 | 登录有效期 24 小时（`web_settings.py` 中的 `session_hours`），手机上几乎每天要重输密码 | 提供“在这台手机上保持登录 30 天”；需权衡共享设备和手机丢失的风险 |
| M-14 | P1 | 只接受 JPEG/PNG/PDF；iPhone 默认 HEIC，部分安卓为 HEIF/WebP。iOS 选图时大概率自动转 JPEG（**需真机验证**） | 前端统一转 JPEG，或后端放开格式 |
| M-15 | P1 | 拍糊了要等分析后才发现 | 上传时检查清晰度和是否整页，不合格当场提示重拍；阈值需用真实卷面确定 |
| M-16 | P2 | 手机上不能看分析结果、不能组卷 | 老师可能想在手机上看一眼结果；作为下一期候选，需先改 PRD |
| M-17 | P2 | 分析完成没有通知 | 微信或短信通知涉及外部服务与个人信息，需单独评估 |

## 3 场景重点与入口突出

原则：每个使用场景只有**一个最显眼的下一步按钮**；按钮文字为“动词＋对象”；不能点的按钮旁边写明还差什么，并给出直达入口；状态标签本身可以点击进入对应操作。所有提示只使用现有接口数据推导，不虚构待办或进度。

### 3.1 按场景的主入口

| 场景 | 设备 | 唯一主按钮 | 现状问题 |
|---|---|---|---|
| 第一次使用 | 电脑 | 添加学生 → 勾选已学考点 → 新建考试（按完成情况依次出现） | 只有“还没有学生”空状态，之后要自己找到考点设置 |
| 考后上传 | 手机 | 上传考试 | 首页“组卷”“新建考试”两个按钮同等大小（已改为“上传考试”主入口＋“组卷”次入口） |
| 补传页面 | 手机 | 继续上传 | 要先进入考试页、找到对应考试、再找上传区 |
| 查看与核对分析 | 电脑 | 去核对第一项 | 待核对内容散落在逐题卡片中，“修正识别”是小号文字链接 |
| 组卷与下载 | 电脑 | 用这次考试组卷 → 下载学生卷 | 分析结果页没有进入组卷的入口；下载链接在结果区中部 |
| 提交反馈 | 电脑 | 提交反馈 | 位于结果最底部，容易被忽略 |

## 4 实施顺序建议

1. **第一批（只改前端，收益最大）**：M-01、M-02、M-05、M-06、E-01、E-08。解决“传得上、看得清、退得回、知道下一步”。
2. **第二批**：M-03、M-04、M-07、M-08、E-03、E-04、E-09，重排手机上传流程；同步更新设计约定中的手机端字号与按钮规范（E-15）。
3. **第三批**：E-02、E-05、E-06、E-07、E-10～E-14，完善电脑端场景衔接。
4. **P1 项**：逐项与用户确认取舍后再排期；M-11 需要后端合同先行。

每批按[改版提示词](ui-refresh-prompts.md)的流程执行：先更新约定，再实现，最后由独立 Agent 用真实页面验收。

## 5 验证方法

- **观察任务**：结合 PRD 计划的约 5 位老师试用。给老师一份试卷和一部手机，只说“把这次考试传上去”，不做演示；再在电脑上说“给这个学生出一份练习卷并下载”。
- **记录**：完成用时、求助次数、点错或传错类型的次数、重拍次数、是否自行找到下一步、是否误按返回键离开。
- **真机覆盖**：至少一台 iPhone 和一台国产安卓，分别用系统浏览器和微信内置浏览器，覆盖拍照、相册多选、HEIC 照片、弱网上传、PDF 下载。
- **结论边界**：界面改版和观察记录只能说明可用性，不等同于老师价值验证。
